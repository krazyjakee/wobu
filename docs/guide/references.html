References & the Board

Images are first-class context, not decoration. A reference carries a role, and the role is what tells the compiler whether it becomes style conditioning, structure conditioning, a colour pass — or something only you ever see.

Adding references

The References tab (⌘2) on any node is a grid. Drag files in from your file manager, or paste from the clipboard. Images are hashed and stored inside the project folder, so two people importing the same reference produce the same file and nothing conflicts.

You can also drag an image onto a node from the Board, or promote a generated image with Pin from the Concepts tab.

Roles

Every reference tile carries a role chip and a weight. The role is the important part — it decides where the image is routed at generation time.

Role Routed to Use it for
silhouette Structure conditioning Body plan and outline — the shape you want held.
palette Colour conditioning A swatch or a painting whose colour relationships you want.
material Style conditioning Surface, weave, glaze, corrosion, wear.
pose Structure conditioning A stance or gesture to copy. Needs a backend with ControlNet.
costume Style conditioning Garment cut, layering, ornament.
mood Nothing — human only Atmosphere you want in your head, not in the model's.
full_ref Character/object reference "This is what it looks like." What a pinned generation becomes.
mood is deliberately inert

A mood reference is never sent to a provider. It exists so you can keep a Bruegel and a photo of a rained-on foundry on the node without them leaking into every render. Not everything on a mood board should be conditioning.

Where references sit in the hierarchy

References inherit exactly like text does. A material swatch on your Culture node reaches every character in that culture. A silhouette reference on a Species reaches every member. Put an image at the altitude where it is true, for the same reasons as notes.

The image budget bites harder than the text budget

Backends cap how many reference images they accept, and they cap them by role. Gemini 3 Pro Image, for instance, allows 6 object references, 5 character references and 3 style references. A five-layer stack can easily offer more style references than that on its own.

So Wobu budgets image fragments per role bucket against whatever the selected backend declares it can take, highest weight first — and the Inspector says so on the layer that lost them: 

Culture · Ember Guild          3/3 style refs · 2 dropped

Silently discarding a reference you deliberately attached would be the worst thing this engine could do, so it never does. If you need a dropped reference, raise its weight or mute a layer that is outbidding it.

Capability differences are visible

A backend with no ControlNet shows your structure references as visibly downgraded to mood-board-only rather than pretending to use them. Aspect dropdowns likewise contain only the selected backend's supported or curated choices and show the dimensions Wobu will actually queue.

The Board

Board mode is a freeform pan-and-zoom canvas — the mood board that normally lives in a separate app and slowly falls out of sync with the project.

  • Drop images anywhere on the canvas; arrange them spatially.
  • Pull in images already attached to nodes to compare them side by side.
  • Drag an image onto a node to attach it as a reference, then set its role.
  • Zoom out for the whole world, in for one culture's costume language.

The Board is where loose visual thinking happens. The References tab is where it gets committed to a node and starts affecting output.

Assets mode

Every image in the project in one filterable grid — imported references and generated results together. Filter by node, by role, by source. This is the fastest way to answer "where did I put that swatch" and to spot a reference that has quietly been influencing more than you meant.

How images are stored

Content-addressed by hash, sharded two levels deep, inside the project folder:

assets/
├── originals/a3/a3f9…c1.png     the file you imported or generated
├── thumbs/a3/a3f9…c1.webp       generated thumbnail
└── meshes/7b/7b21…04.glb        concept 3D output

Two consequences worth knowing. Deduplication is free — importing the same image twice costs one file. And asset writes can never conflict, because the same bytes always land at the same path, which is what makes shared project folders safe.

Thumbnails live in the project folder rather than in local cache on purpose: the first person to import an image pays the cost of generating them and everyone else on the share gets them for free. Grids bind to thumbnails only; full-resolution originals are fetched one at a time when you actually open an image.
